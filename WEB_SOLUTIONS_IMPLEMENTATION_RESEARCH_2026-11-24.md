# Исследование разработанных решений для нового Web-приложения «Контракты ИП»

**Дата:** 24.11.2026. **Статус:** техническое исследование и реестр решений для будущего проектирования, НЕ внедрение. **Область:** отдельная локальная Web-версия (HTML/CSS/JS + PowerShell/Excel), не Desktop/Tkinter. Ни код работающих программ, ни пользовательские базы/документы, ни VERSION не изменять в рамках данного исследования.

## 0. Исходная база и границы достоверности
Изучены текущие AGENTS.md, PROJECT_STATE.md, README.md, VERSION (Desktop 2.23.20), отчёты WEB_ARCHITECTURE_RESEARCH.md, WEB_RESILIENCE_RESEARCH_2026-11-24.md, WEB_EXCEL_SQLITE_MIGRATION_RESEARCH_2026-11-24.md, WEB_STOCK_FINANCE_RESEARCH_2026-11-24.md и предоставленная локальная «Исследование_функций_Контракты_ИП_2026-11-24.md» (F01–F34). Выборочно независимо повторно открыты *конкретные исходники* InvenTree, HomeBox, ERPNext, excel-to-domain-models и openstock через GitHub; проверены официальные SQLite, openpyxl, Microsoft Excel, PyInstaller, OWASP и restic. Ранее исследованный server.ps1 содержит 4139 строк, но в этом сеансе его полная текущая копия, исходный XLSX, все JSON, frontend и документация фактических API не доступны: полнота совместимости с действующей Web-программой **не установлена**.

## 1. Оценка альтернатив и выбор основы

| Кандидат | Изученный механизм | Применение | Ограничения |

| Restic | check, check --read-data, restore | Вторичная проверяемая копия после базового собственного backup | Внешняя утилита и ключи; не заменяет снимок SQLite+документов |
| Litestream | репликация WAL | Только опция второго этапа | Усложняет фоновую работу и откат, не замена восстановления документов |
| Grocy, HomeBox UI | небольшое локальное browser-first приложение | Оставить существующий HTML/CSS/JS | Не наследовать чужую модель предметной области |
| daryne01/excel-to-domain-models | src/parsers/base.py: заголовки вне первой строки, разбор Decimal, отбор итоговых строк; costing_engine.py: проверяемое округление ROUND_HALF_UP | Strict Extract–Normalize–Validate–Stage–Reconcile | Правила blank_is_zero и ROUND_HALF_UP сверять с реальными формулами, не считать универсальными |

| Alembic/sqlite-utils | версии схемы и техническая диагностика | Рассмотреть при появлении нужды | Не вводить ради моды; PRAGMA user_version достаточно для малого проекта |

**Решение по стеку:** оставить текущий браузерный UI, перейти на локальный Python backend с версионированным JSON API и отдельными domain/services/repository уровнями, SQLite для операций, папку attachments для файлов. Начинать с минимальных зависимостей. Никакой тяжёлой ERP, Electron, обязательного облака или общей БД с Desktop. Windows/macOS — отдельные пакеты одного backend; PyInstaller не cross-compiler.

## 2. Список решений для будущего внедрения с проверяемой логикой

### D01. Контракты, черновики, два режима цены
- Не сохранять совсем пустую новую карточку; неполную, но непустую — сохранять как черновик без дублей.
- Товары: количество >0; поддерживать ввод «цена за единицу» и «сумма позиции». При округлении цены до копеек введённая сумма остаётся первичным значением. Источник последнего редактирования сохранять для позиции.
- Нельзя выводить дату отправки/оплаты из статуса, если исторической даты нет; сохранять дату события и время его регистрации отдельно.
- Не переносить автоматически цепочку состояний Desktop на Web; картографировать реальные статусы Web.

### D02. Идемпотентные HTTP-команды и конкурентные правки
- Для каждой операции operation_id UUID + canonical payload_hash + result; UNIQUE(operation_id).
- Повтор идентичной операции выдаёт исходный результат; тот же operation_id с иным содержимым — HTTP 409.
- Для изменения карточки/расхода revision/If-Match; при конфликте возвращать текущую версию и позволять безопасно сверить изменения, не перезаписывать молча.
- UI блокирует вторую отправку для удобства, но сервер обеспечивает безопасность независимо от UI. Проверить двойной клик, timeout после COMMIT, две вкладки, crash/retry.

### D03. Остаток, резерв и дефицит
- physical_qty >=0, reserved_qty >=0, available_qty=physical_qty-reserved_qty, shortage=max(0,-available_qty).
- **Отрицательное available допустимо** как сигнал дефицита; списывать в физический минус нельзя.
- Приход допустим даже при отрицательном доступном остатке.
- Защищать резерв другого контракта; при нескольких товарных строках проверять все товарные ID и все доступные к списанию значения внутри одной транзакции.
- Отображение склада на главной, вкладке, уведомлениях — единый сервис/снимок; текущий склад не фильтровать по месяцу финансов.

### D04. Отгрузка, возврат и повторная отгрузка
- BEGIN IMMEDIATE → перечитать карточку/ревизию → проверить статус, партии, физические остатки и выделения → записать события и себестоимость → обновить статус → COMMIT.
- Обеспечить уникальность бизнес-операции для одного цикла отправки; не запрещать новый цикл после настоящего возврата.
- Отправлено, вручено, оплачено — разные события; вручение/оплата не должны задним числом создавать неподтверждённую отгрузку.
- При ошибке в любой позиции ROLLBACK всей операции; HTTP 200 только после COMMIT.

### D05. Неизменяемый исходный журнал и исправления ошибок
- Сохранять исходный receipt + отдельную историю correction events; «эффективную историю» рассчитывать применением последней валидной коррекции к исходному приходу.
- В отчёте «Движение по складу» показывать фактические приходы, отправки, возвраты; корректировка ошибки не становится второй реализацией.
- При редактировании старого прихода репроецировать хронологию количеств/стоимости вперёд; если возникает отрицательный исторический physical, отклонить всю коррекцию.
- Инвентаризационная разница и настоящий возврат — самостоятельные виды операций, не подменять ими правку ошибочного ввода.

### D06. Себестоимость
- Сохранить текущую Web-методику средневзвешенной стоимости (в копейках; округление AwayFromZero); при последнем списании остатка брать *всю остаточную стоимость*, чтобы не оставлять стоимость без товара.
- Возврат относить по фактической стоимости исходной отгрузки; после исправления старой закупки пересчитать затронутые отгрузки, возвраты и прибыль.
- Удерживать один источник истины себестоимости, запрещать двойной учёт логистики/комиссии/прочих расходов.
- **Не менять** на FIFO, LIFO или бухгалтерское округление «по умолчанию» без сравнения с текущим Web.

### D07. Финансы и периоды
- Контрактная выручка, стоимость товаров, логистика, комиссии, налоги, прочие расходы — самостоятельные категории с ключами операций.
- Деньги в целых копейках или Decimal, без binary float; NULL ≠ 0; явно хранить точность и правила округления.
- Годовые налоговые настройки, дата признания и отложенные контракты — **только после карты текущих формул**. Фактические пользовательские ставки не приравнивать к действующему налоговому законодательству.
- Расход с amount, month, operation_id, revision; повторный запрос не создаёт дубль. После сохранения месяц и KPI пересчитываются, но «живой склад» остаётся актуальным.
- Сверять доходы, себестоимость, налоги, расходы, чистую прибыль по каждой сделке/месяцу, а не только общую цифру.

### D08. Документы и безопасность файлов
- Стабильный document_id; original_filename отдельно от storage_filename; относительный путь; размер; SHA256; attachment contract_id.
- Сначала stage временный файл и hash; в транзакции зарегистрировать манифест; затем проверяемо финализировать операцию с восстановлением/компенсацией при ошибке. SQLite и файловая система **не образуют одну ACID-транзакцию**.
- Загрузка без обязательного вложения; ошибки отсутствующих *ранее прикреплённых* файлов показывать явно. Запрет path traversal/архивных ссылок/небезопасных путей и открытие только разрешённых файлов.
- Архив с отсутствующим документом может быть только «неполным» с перечислением исключений, не «полным и проверенным».

### D09. Резервные копии и восстановление
- Backup исходной активной SQLite делать через Online Backup API, а не простым копированием рабочего .db в WAL; обеспечить согласованность с вложениями через краткую приостановку изменяющих операций и снимок реестра файлов.
- Manifest: schema_version, app_version, создано_UTC, UUID комплекта, item_count, file list (пути/размеры/SHA256), количество карточек/строк/документов, ошибки.
- Временный архив → SHA256, integrity_check, foreign_key_check → атомарное переименование в «готовый архив»; резерв на второй физический носитель.
- Настоящий контроль — **пробное восстановление в отдельную папку** и независимая сверка документов/контрактов/остатков/финансов; тест обрыва архива и недостатка места.
- Restic опционально для внешней копии, с регулярным check --read-data и тестовым restore; облако не обязательно.

### D10. Excel → SQLite
- Никогда не изменять оригинальный XLSX; копия источника и исходных JSON/docs с SHA256; только read-only разбор и новая staging SQLite.
- Скан листов, источников дат, формул и cached values, точности идентификаторов, видов Excel epoch 1900/1904, конфликтующих сумм, пустых/нулевых значений, ссылок на документы.
- Excel ограничен ~15 значащими цифрами в numeric; текстовые идентификаторы не переводить в float. Невосстановимые исходные цифры не угадывать.
- Построчное сопоставление поля и происхождения (workbook/sheet/cell/source record), отдельно аудит листов-итогов/шаблонов; отчёт всех ошибок, ничего не отбросить молча.
- Независимая сверка: контракт/товары/резерв/отгрузки/приходы/возвраты/финансы/каждый месяц/каждый существующий документ.
- No destructive import, --force, silent overwrite или двух одновременно активных писателей. Переключать программу только при **нулевых необъяснённых расхождениях** и с проверенным откатом.

### D11. Безопасность localhost
- Bind 127.0.0.1 (и при необходимости ::1 с отдельным тестом), запрещать 0.0.0.0 по умолчанию.
- Строго проверять Host (localhost/127.0.0.1 и установленный порт), Origin и Fetch Metadata для изменяющих запросов; anti-CSRF token/привязка к сессии; отсутствие wildcard CORS.
- Если предполагается подключение из LAN, это **отдельное** решение с аутентификацией и TLS, не случайная побочная функция.
- HTTP API валидирует тип, сумму, дату, quantity, ID и полномочия; не доверять UI; ограничения путей. Тестировать внешнюю страницу, DNS rebinding, CSRF, XSS и архив ZIP-bomb.

### D12. SQLite, релизы, перенос Windows/macOS
- Foreign keys включить **на каждом соединении** и проверять, busy_timeout, CHECK, UNIQUE, user_version, управляемые миграции; отдельный журнал ошибок; не скрывать SQLITE_BUSY.
- WAL-reset bug в SQLite <=3.51.2 (официально исправлен 3.51.3 от 13.03.2026); в производственной сборке проверять фактический sqlite3.sqlite_version, не только Python. Избирать поддерживаемую исправленную версию, проверять её контрольными тестами.
- Для разных ОС упаковка отдельно, PyInstaller не cross-compiler; Documents/данные в пользовательской папке, не в временной распаковке; перенос через проверенный архив без абсолютных путей.
- Повторный запуск не создаёт двух писателей на одном файле; graceful shutdown и восстановление после sleep/resume; GUI/browser ошибка должна быть понятной.
- Изменение VERSION/Desktop релиза запрещено этим исследованием; новый Web должен иметь собственную схему версионирования.

## 4. Испытания: блокирующая матрица
1. **Контракт:** пустой/черновик; двусторонняя цена и сумма; повтор 2/10 кликов; две вкладки; перезапуск; потерянный HTTP-ответ после commit.
2. **Склад:** физ 100/резерв 120 → доступно −20; приход 30 → доступно 10; чужой резерв; два товара с ошибкой второй строки; прямое вручение без исторической фальсификации; отгрузка/возврат/новая отгрузка; ошибка после записи половины строк → rollback.
3. **История:** правка старого прихода, новая хронология; запрет исторического минуса, дробные копейки, отгрузка всего остатка, точный возврат; сверка UI/API/БД.
4. **Финансы:** месяц регистрации vs платежа; два соседних года/налоговые ставки; затраты/налоги по каждой сделке; исправление расхода через revision; повтор idempotency; копейки на каждой стадии.
5. **Документы:** 0/1/100 файлов, пропавший/изменённый файл, одинаковое имя, кириллица, ссылки выше root, zip-slip/zip-bomb, восстановление полного пакета.
6. **Миграция:** старые/новые формы Excel, 1900/1904, пустой формульный кэш, ID >15 знаков, нулевые и отсутствующие суммы, дубли, старые ссылки, авария во время импорта, повторный импорт без дублей.
7. **Устойчивость:** внезапное завершение до/после COMMIT, одновременные запросы, SQLITE_BUSY, заполненный диск, прерванный backup, выключение/пробуждение, Windows/macOS пакет.
8. **Безопасность:** Host/Origin/CSRF, XSS, доступ к чужим файлам через path traversal, посторонний сайт, отсутствие открытого LAN.
9. **Нагрузка:** 1 000+ искусственных контрактов, 10 000+ движений; фиксировать реальные p95 ответа и время восстановления, не заявлять производительность без измерений.
10. **Регрессия:** полный сценарий создать → добавить товар → резерв → отправить → вручить → оплатить → сверить склад+себестоимость+налоги; результаты каждого теста фиксировать по commit и окружению.

## 5. Порядок будущих работ и критерии выпуска
- **R0 / READ-ONLY**: точная карта текущих server.ps1 endpoints, фронтенда, Excel sheets/columns, JSON, папки документов, выражений расчётов и функций исправления.
- **R1 / PROTOTYPE**: отдельно от продуктивных данных реализовать минимальную SQLite модель склада/финансов с транзакциями, reconciliation и граничными тестами.
- **R2 / SHADOW**: создать проверенный снимок исходных файлов; одноразовый детерминированный импорт в staging; отчёт о каждой неоднозначности/расхождении.
- **R3 / PARITY**: одинаковый неизменяемый набор → старая Web и новая тестовая Web, сравнение API/финансов/товаров/периодов по полям.
- **R4 / UX/SECURITY**: подключить существующий UI без необязательных новых модулей; тестировать браузерную доступность, клавиатуру, localhost/CSRF.
- **R5 / DISASTER RECOVERY**: автоматический архив и тестовое полное восстановление, сквозная регрессия на Windows/macOS, failpoint tests и пакетирование.
- **R6 / CUTOVER**: только отдельно согласованное переключение при нулевых необъяснённых расхождениях, с сохранением Excel и откатной копии; без автоматической публикации/замены рабочей БД.

**Блокеры к переносу реальных данных:** оригинальные фактические листы/поля и формулы ещё не сверены; данные в текущем исследовании отсутствуют; текущий Web сервер исходно 4139 строк проинспектирован только частично в предыдущем исследовании. Нельзя считать полный аудит, интеграционные проверки, миграцию, Windows/macOS или восстановление выполненными.
