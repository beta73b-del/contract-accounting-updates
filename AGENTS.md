# Правила разработки «Учет заключенных контрактов»

## Начало и завершение работы

- Перед изменениями прочитай `PROJECT_STATE.md`, `CHANGELOG.md`, `README.md`, актуальные `VERSION` и `app/app_version.py`. Сверь состояние с GitHub, не полагайся только на историю чата.
- Общайся с пользователем по-русски. Реализуй согласованную задачу и выполни соответствующие проверки.
- Различай требование, наличие реализации, успешный тест и подтверждение пользователя на его компьютере. Не называй функцию проверенной только по описанию релиза.
- После завершения задачи обновляй `PROJECT_STATE.md`; после выпуска версии — также `CHANGELOG.md`. Сохраняй в Git историю решений и незавершённые шаги.
- При конфликте старых требований с новым указанием пользователя следуй новому указанию; зафиксируй изменение. Неразрешённые расхождения перечислены в `PROJECT_STATE.md`.

## Стек и изменения

- Приложение для Windows: Python, Tkinter, SQLite, PyInstaller onefile. Сборка текущего релиза использует Python 3.11.
- Основные файлы: `app/main.py` — интерфейс; `app/db.py` — данные, миграции, склад и итоги; `app/calculations.py` — расчёты; `app/reminder_worker.py` — сводки; `app/auto_update.py` — обновления; `app/spellcheck.py` — орфография.
- Не переписывай приложение целиком ради локального исправления. Сохраняй существующие функции и совместимость пользовательских баз.
- Версии в `VERSION` и `app/app_version.py` должны совпадать. Изменение `VERSION` в `main` запускает публикацию EXE; меняй его только в рамках согласованного выпуска.

## Пользовательские данные

- Не коммить реальные базы, архивы резервных копий, вложения, журналы с личными данными, пароли и почтовые настройки. Проверки выполняй на синтетических данных или локальных копиях.
- Рабочая база Windows: `%LOCALAPPDATA%\UchetZakupok\zakupki_work.db`; путь может быть переопределён `ZAKUPKI_LOCAL_DATA`.
- Рядом с EXE: `data/zakupki.db` — закрытая копия для синхронизации; `data/attachments` — документы; `data/backups` — резервные копии. Не подменяй рабочую базу случайной или временной копией.
- Перед миграцией или исправлением базы делай отдельную резервную копию. Проверяй целостность SQLite, сохранение записей, количеств, цен, связей и вложений.
- При конфликте локальной и облачной копий сохраняй обе; не разрешай конфликт молчаливой перезаписью.
- Обновление EXE не должно заменять базу, документы и пользовательские настройки.

## Правила предметной области

- Используй название «Учет заключенных контрактов», раздел «Контракты» и терминологию текущего интерфейса.
- Неполная карточка остаётся черновиком и логируется как сохранённый черновик. Полностью пустая новая карточка при закрытии не создаёт запись. Существующий технический черновик обновляй, не создавай дубль.
- Сохраняй карточку при закрытии. Незавершённая строка товара с количеством ≤ 0 блокирует закрытие с понятным сообщением.
- Основная цепочка: «В процессе → Отправлено → Вручен → Исполнено». «Вручен» не равно «Исполнено»: окончательное исполнение требует оплаты заказчиком.
- Отдельный этап и таймер приёмки не добавляй. После вручения контролируй единый конечный срок оплаты, уже включающий приёмку.
- «Подписать до» необходимо сохранить. Частичная оплата не предусмотрена.
- Товар до отправки резервируется. Фактическое списание выполняется однократно; дальнейшая смена статуса не списывает его повторно. Прямой переход в «Вручен» в текущем коде также фиксирует пропущенный этап отправки.
- Обеспечение задаётся для товарной позиции: «Со склада», «Требуется закупка», «Отложенная закупка». Сохраняй разделение физического остатка, резерва, доступного остатка и будущей потребности.
- При отрицательном доступном остатке в «Требует внимания» показывай «Не хватает N шт.» с положительным N для любого товара; уведомления должны использовать тот же смысл.
- Канонические названия: «Рутокен Lite 1010», «Рутокен ЭЦП 3.0 3120». Известные варианты одной модели объединяй без потери истории. Склад допускает и другие товары; не объединяй разные модели по нечёткому совпадению.
- KPI и итоги должны согласовываться с выбранным периодом и детализацией. Логистика, комиссии, налоги и прочие расходы влияют на прибыль. Правило месяца отложенных контрактов требует отдельного согласования — см. `PROJECT_STATE.md`.
- Прочий расход добавляется суммой в выбранный месяц с явным подтверждением и немедленным пересчётом итогов.
- Вложения необязательны: отсутствие документов само по себе не блокирует контракт. Сохраняй открытие через ОС, выгрузку и видимость выбранного имени.
- Не добавляй без нового запроса dashboard, поиск, отдельную задолженность, шаблоны, отдельный архив или частичную оплату.
- Сохраняй Ctrl+C, вставку из буфера, прокрутку карточки, читаемые поля, переносы строк, формат дат DD.MM.YYYY, суммы с разделителями и количества без лишнего `.0`.

## Проверки и выпуск

- Выполняй `python -m compileall -q app` и проверки, соответствующие затронутой логике. Для склада проверяй резерв, списание, дефицит, движение и стоимость; для итогов — периоды, налоги и расходы; для сохранения — пустую карточку, черновик и повторное закрытие.
- Скрипты регрессии находятся в `tests/` и запускаются отдельно командой `python tests/<имя>.py`. Некоторые проверки требуют Windows: не выдавай их недоступность на Linux за успешное прохождение.
- Windows-сборка должна проверять включённые Python/Visual C++ DLL и реальный запуск EXE. Для OTA проверяй установку и откат с унаследованным onefile-окружением и появление главного окна, а не только живой процесс.
- Независимый перезапуск после onefile обязан сбрасывать служебные `_PYI_*`/`_MEIPASS2` и устанавливать `PYINSTALLER_RESET_ENVIRONMENT=1`. Не изменяй окружение текущего приложения ради дочернего процесса.
- Не публикуй сборку при проваленных обязательных проверках. В отчёте называй выполненные проверки, ограничения и ссылку на релиз; не утверждай, что новая версия установлена у пользователя без его подтверждения.
