# Исследование №4: целостность склада и финансов Web «Контракты ИП»
Дата: 24.11.2026. Только исследование. Рабочий XLSX, документы, код Web и Desktop, VERSION и релизы не изменялись. Миграция не выполнялась.

## Источники
- [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [isolation](https://www.sqlite.org/isolation.html), [foreign keys](https://www.sqlite.org/foreignkeys.html): BEGIN IMMEDIATE, транзакционный откат, ограничения, обработка SQLITE_BUSY.
- [ERPNext immutable ledger](https://docs.frappe.io/erpnext/immutable-ledger-in-erpnext): история отмены операций. Не копировать модель сторно буквально: Web исправляет исходную проекцию ошибочного прихода.
- [Odoo reservations](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/inventory/shipping_receiving/reservation_methods.html), [Odoo valuation](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/inventory_valuation/operations_valuation.html): раздельные резервы, фактические движения и стоимость.

## Фактический Web-код
На подключённом Windows ПК в режиме чтения изучен server.ps1 (4139 строк) из каталога Web-приложения, без чтения/записи XLSX. Stock-Model: сохраняет исходные события, применяет последнюю editReceipt/deleteReceipt к исходному приходу, пересчитывает историю; коррекции не суммируются вторично; запрещает физический отрицательный остаток и отрицательную стоимость, допускает отрицательный available=quantity-reserved; считает shortage=max(0,-available). Stock-Cost: пропорциональная средневзвешенная стоимость в копейках с округлением AwayFromZero, при полном списании берётся вся остаточная стоимость. Stock-ShipLines: физический остаток и защита чужих резервов. Stock-PlanRecord: отгрузка после действующего резерва и явного подтверждения, последующие вручение и оплата не списывают повторно; отмена отправки требует подтверждённого возврата; старые вручённые контракты без подтверждённой отгрузки сохраняются без выдумывания исторического события. Finance-Model/Finance-Mutate: журнал FinanceLedger-v1, id операции, проверка совпадения payload при повторе, оптимистическая ревизия расхода; ставки задаются по году согласно имеющейся логике программы (не вывод о применимой ставке налога по закону).
Не проверены все endpoints, UI, источники всех дат и финансовых формул, реальный XLSX и полный жизненный цикл.

## Проектные требования
- Сохранить исходный журнал и его эффективную проекцию; аналитика фактического движения не должна представлять исправление ошибки как отдельную реализацию. Реальный возврат и инвентаризационная разница требуют отдельного отражения в сверке остатков.
- Атомарная операция в SQLite: идентификатор и нормализованный payload, проверка ревизии, статус, резерв, складские события, расчёт стоимости, commit. Повтор того же op ID с тем же payload возвращает прежний результат; конфликт payload отклоняется. Проверять все товарные позиции в одной транзакции. Учитывать отдельные циклы отгрузка-возврат-новая отгрузка, а не запрещать новую отгрузку навсегда.
- Дефицит доступного остатка разрешён, физический — нет. Не менять метод оценки стоимости или даты признания расходов/прибыли без сверки с Web.
- Переоценка после исправления исторического прихода должна пересчитать затронутые исходящие движения и стоимость возврата, отчёты и зависимые показатели. При невозможности восстановить непротиворечивую историю отклонить целиком.
- Не переносить правила Tkinter автоматически в Web. Для новых записей явно хранить дату факта, дату регистрации и ревизию, не фабриковать отсутствующую историческую дату.

## Эксперимент
Фактически выполнены 12/12 unittest в Linux, Python 3.13.5, SQLite 3.46.1, :memory:. Искусственный прототип, не код приложения. Проверки: приход при отрицательном доступном остатке; исправление и удаление прихода; защита чужого резерва; повторная отправка; конфликт op ID; откат при искусственном сбое; запрет исторического дефицита; округление при дробной себестоимости и полное списание; возврат по стоимости отгрузки; конфликт ревизии расхода; integrity_check и foreign_key_check. Все PASS. Прототип не моделирует полный многопозиционный контракт, все возвратные циклы, хронологию, периоды, HTTP, WAL, Windows/macOS или реальный Excel; не применять в производстве. SQLite 3.46.1 не является исправленной версией относительно WAL-reset дефекта из исследования №2. Исходник тестов выдан пользователю отдельно в чате.
