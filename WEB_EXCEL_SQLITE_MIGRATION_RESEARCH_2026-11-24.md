# Исследование №3: безопасная миграция Web «Контракты ИП» с Excel на SQLite

**Дата:** 24.11.2026. **Статус:** исследование источников, просмотр конкретных файлов GitHub, 11 испытаний отдельного синтетического прототипа. **Миграция пользовательских данных не выполнялась.** Это не одобренное внедрение.

## 0. Границы и источники правды

- Предмет исследования — **локальная браузерная Web-версия «Контракты ИП»**: текущий HTML/CSS/JS, PowerShell `server.ps1` + Excel COM, XLSX `data/База_контрактов.xlsx`, документы в отдельной родительской папке и вспомогательные JSON. Это **не** настольный Tkinter/SQLite-проект из данного GitHub-репозитория.
- Точную структуру рабочего XLSX, поля фактического `server.ps1`, все API и алгоритмы начисления прибыли в этом исследовании **не инспектировали**. Не выдавать предложенную схему БД за готовое отображение реальных данных. Перед разработкой просмотреть актуальный код Web и *отдельный неизменяемый снимок* рабочей книги.
- Рабочий XLSX, документы, PowerShell, Tkinter/SQLite, версии и релизы не изменены. В GitHub публикуется только этот документ и ссылка на него.
- Дополнительные исследования: [WEB_ARCHITECTURE_RESEARCH.md](WEB_ARCHITECTURE_RESEARCH.md), [WEB_RESILIENCE_RESEARCH_2026-11-24.md](WEB_RESILIENCE_RESEARCH_2026-11-24.md).

- [src/warehouse/loaders.py](https://github.com/daryne01/excel-to-domain-models/blob/main/src/warehouse/loaders.py): парсинг отделён от записи в БД; `transaction.atomic`, `update_or_create`, запись происхождения source_workbook/source_sheet/source_row.
- [tests/test_warehouse.py](https://github.com/daryne01/excel-to-domain-models/blob/main/tests/test_warehouse.py): повторный импорт обновляет существующие записи, а не дублирует их; отчёт происхождения записи.
- [src/costing_engine.py](https://github.com/daryne01/excel-to-domain-models/blob/main/src/costing_engine.py) и [tests/test_costing_engine.py](https://github.com/daryne01/excel-to-domain-models/blob/main/tests/test_costing_engine.py): сравнение **каждого промежуточного шага** модели прибыли с результатами формул, вычисленными самостоятельным табличным движком; округление `ROUND_HALF_UP` применяется там, где оно соответствует исходным формулам.

**Для Web «Контракты ИП»:** сохранять происхождение каждой записи; отдельно читать, нормализовать и валидировать строки; сверять по контрактам/товарам/месяцам себестоимость, логистику, комиссию, налог, прочие расходы, сумму, прибыль и рентабельность, а не только общий итог. В отчёте должны быть не только успешно перенесённые строки, но и *все* замечания, которые не должны скрыто превращаться в нули.

**Важное отличие:** для разовой миграции в отдельный staging-файл предпочтительнее **отказаться от изменения ранее импортированного исторического факта при конфликте ключа**, а не автоматически применять `update_or_create`. `source_row` — метаданные для трассировки, но не гарантированно стабильный идентификатор после сортировки Excel. Ключи следует определить по реальной логике Web, не просто по номеру контракта.

## 2. Официальные ограничения Excel (критичные для миграции)

1. **Формулы:** [openpyxl](https://openpyxl.readthedocs.io/en/stable/tutorial.html) по `data_only=False` читает формулы, по `True` — последний сохранённый результат. Это не независимый пересчёт. Нельзя изменять исходный XLSX ради `load_workbook/save`: библиотека предупреждает, что некоторые объекты/фигуры могут потеряться при сохранении. Требование: **только чтение отдельной копии; ни одного вызова save() на источнике**.
2. **Номера/идентификаторы:** [Microsoft о сохранении ведущих нулей и длинных чисел](https://support.microsoft.com/en-gb/excel/keeping-leading-zeros-and-large-numbers) — Excel может терять ведущие нули и имеет только 15 значащих цифр для числовой ячейки. Номер контракта, ИНН/ОГРН, банковские и серийные номера — TEXT; не приводить к float/int. Если цифры **уже потеряны в Excel**, мигратор не имеет права «восстанавливать» их догадкой.
3. **Даты:** [Microsoft Excel Date Systems](https://support.microsoft.com/en-gb/excel/date-systems-in-excel) — существуют системы 1900 и 1904, их смещение 1462 дня; проверять workbook epoch, тип ячейки, строковые даты `ДД.ММ.ГГГГ` и явные пустые даты.
4. **Деньги:** `Decimal` и точная сумма в копейках; учитывать значения с запятыми/пробелами и различать `NULL`, `0`, отрицательные корректировки и незаполненные расходы. Правила округления / сохранения суммы позиции **сверить с фактическим текущим Web-кодом**; не переопределять бизнес-правило сторонним калькулятором.
5. **Периоды:** даты подписания, отправки, вручения, оплаты, реального прихода и расхода не выводить из одного статуса по догадке. Ключ признания отложенных контрактов **не менять без отдельного согласования**.

## 3. Предложение для будущего одноразового перевода (не реализовано)

1. Согласованно закрыть/приостановить запись в действующей Excel-программе **лишь на согласованном этапе переключения**; сначала безопасная копия оригинального XLSX + документов + JSON и SHA-256. До этого исследовать только ранее существующий безопасный снимок.
2. Изолированный READ-ONLY экстрактор: ведомость листов, заголовков, типов ячеек, формул/кэшей, внешних ссылок, исходных значений и идентификаторов; журнал происхождения.
3. Промежуточный набор нормализованных записей со строгой схемой и **отчётом предупреждений/ошибок**; любую неразобранную запись помечать для разбора, не исключать и не заменять нулём.
4. Создание нового SQLite **в staging-пути, отличном от любой действующей БД**; схемные версии, `FOREIGN KEY`, `UNIQUE`, `CHECK`, `BEGIN IMMEDIATE`, журнал операций; исходный файл не удаляется и не модифицируется.
5. Раздельный импорт исходной истории товаров, приходов, резервов, отгрузок, возвратов, оплат и дополнительных расходов. Не «создавать» задним числом реальные складские движения только по конечному статусу, если в Excel есть отдельные факты.
6. Документы: сохранять реальные относительные ссылки на родительскую папку `Документы`; вычислить SHA-256 каждого *имеющегося* файла; отсутствие файла — **явное исключение в отчёте**, не автоматическая очистка ссылки/удаление контрактной карточки.
7. Независимая ведомость сверки **для каждой** строки контракта/товара, месяца и суммы: количество исходных/новых записей, записи без связи, резерв+физический+доступный, вход/расход, оплачено, себестоимость, налоги, прибыль; отличия разбирать до перехода.
8. `PRAGMA integrity_check` и `PRAGMA foreign_key_check`, подтверждённый backup/restore staging; негативные сценарии.
9. Параллельная проверка **в тестовом окружении**: одинаковые UI/API-ответы старой Excel и новой SQLite-версий на согласованном неизменяемом снимке; не запускать два автора на одной рабочей базе.
10. Только после отдельного подтверждения успешной миграции переключить локальный Web-сервер на SQLite; сохранить Excel/XLSX и резервную копию для отката. Никаких команд `--force`/удаления исходной БД.

**Необходимые нерешённые вопросы:** реальные листы и схемы XLSX; наличие формул/динамических вычислений; особенности источника серийных номеров; точные поля затрат и налогов; формат ссылок `docs:` и вспомогательных JSON; порядок исторических исправлений и отмен статусов; существование дублей и неопределённых внешних ссылок. Без чтения фактических источников нельзя давать карту миграции «колонка → поле SQLite».

## 4. Синтетический независимый эксперимент (выполнен в изолированной среде)

**Среда:** Linux x86_64, Python 3.13.5, sqlite3 runtime 3.46.1. **Только искусственные Python-словари с формой предполагаемого результата чтения XLSX + SQLite `:memory:`**; реальный XLSX, COM, PowerShell, Windows/MacBook не использованы; это **не испытание реальной миграции Excel**.

Модель включает `contracts`, `items`, `docs`, ограничения `FOREIGN KEY`, `CHECK(qty>0)`, атомарное `BEGIN IMMEDIATE/COMMIT/ROLLBACK`, суммы целыми копейками, строгий формат дат и запрет перезаписи отличающейся исторической записи при повторном импорте.

**Фактически выполнены 11 тестов, все PASS:**

1. Ведущие нули номера `0000123` сохраняются, два разных контрагента могут иметь одинаковую строку номера;
2. Две суммы `1000,10` и `2050,00` дают **305010 копеек**;
3. Второй импорт не создаёт новых контрактов/позиций/документов;
4. Невалидная сумма (`NaN`) откатывает **всю** миграционную транзакцию;
5. Отсутствующее обязательное для архива вложение вызывает ошибку и откат (это не запрещает карточки без вложений);
6. Исторический конфликт суммы при повторном импорте **отклоняется без перезаписи**;
7. Нарушение внешнего ключа откатывает всю миграцию;
8. Отрицательное, нулевое и дробное количество (для штучного товара) отвергается;
9. Число с третьим десятичным знаком `2.665` помечается как неопределённая точность вместо скрытого округления; для реальных цен правила уточнить по действующей программе;
10. `24.11.2026` сохранено как `2026-11-24`, отсутствие даты остаётся `NULL`;
11. Невозможная дата `31.02.2026` вызывает полный откат.

**Важно:** код испытаний создан временно, не установлен в проект и не опубликован как тестовая инфраструктура. Это демонстрация свойств предлагаемого подхода, а не сертификация. В синтетической модели пока нет реальных резервов, складского журнала, месячных фин. отчётов, PDF и Excel formula cache. Использованная версия SQLite 3.46.1 **не является патченной относительно редкого WAL-reset дефекта**; тесты в `:memory:` не оценивают риск WAL.

## 5. Дополнительная рекомендация по надёжности и лицензиям

- Специализированный импортёр для **одной известной книги** безопаснее автоматического «универсального» поиска столбцов по нечёткому совпадению. Любая неоднозначность — ошибка + ручной разбор.
- Отдельно вести **две ведомости**: (а) данные как были в Excel; (б) рассчитанные уже новым Python-кодом. Несовпадения не маскировать.
- Не импортировать сторонние коммерческие/налоговые правила. Наша система имеет собственные условия признания, УСН, логистики, комиссии, даты оплаты и резерва.
- Репозитории-кандидаты маленькие и не проходили наш security audit. Заимствуются **идеи, тестовые свойства и ссылки**, не сторонний исходный код.
- Отдельный Desktop/Tkinter/SQLite репозиторий пользователя не служит источником истины по Web-версии и не должен изменяться автоматически.

**Следующее направление исследования:** исходный `server.ps1` и схематизация реального XLSX на **безопасной копии**, без миграции рабочей базы; подготовка полной независимой матрицы сверки `Excel ↔ SQLite` и негативных испытаний импорта.
