## Граница проекта
Это относится к отдельному **браузерному приложению «Контракты ИП»** (HTML/CSS/JS, локальный PowerShell-сервер, Excel COM и XLSX на Windows), а **НЕ** к настольному Tkinter/SQLite-приложению «Учет заключенных контрактов» из данного GitHub-репозитория. ## Проверенные образцы реализации (изучены файлы репозиториев)

### 1. InvenTree: атомарное резервирование и единственное завершение отправки
- Исходник резервирования: [order/serializers.py, строки 2038–2063](https://github.com/inventree/InvenTree/blob/adfd393c92e70f4252b38c3373d3d671f56c844c/src/backend/InvenTree/order/serializers.py#L2038-L2063). В транзакции блокируется товарная запись, заново проверяются существующие выделения, затем создаётся выделение.
- Исходник отгрузки: [order/tasks.py, строки 240–287](https://github.com/inventree/InvenTree/blob/adfd393c92e70f4252b38c3373d3d671f56c844c/src/backend/InvenTree/order/tasks.py#L240-L287). Внутри транзакции блокируется отгрузка и проверяется флаг её завершения; повторный вызов пропускается, затем отмечается завершение.
- Для нас: единая транзакция на изменение статуса контракта, создание/освобождение резерва и движение товара; уникальная бизнес-операция отгрузки с гарантией **не больше одного** списания; повторное «Отправлено»/прямое «Вручен» не должно списывать второй раз. Проверить дефицит, возвраты, частичное редактирование, восстановление после аварии.
- Важно: исходник на Django с `select_for_update()`; **SQLite не поддерживает это средство блокировки строк**. Нельзя переносить код буквально. Для SQLite проектировать `BEGIN IMMEDIATE`, короткую транзакцию, ограничения `UNIQUE`, ревизии записей и повторную проверку при записи. См. [SQLite isolation](https://www.sqlite.org/isolation.html) и [Django QuerySet API](https://docs.djangoproject.com/en/dev/ref/models/querysets/#select-for-update).

### 2. ERPNext: тест идемпотентности повторного добавления
- [tests/test_mapper.py, строки 52–70](https://github.com/frappe/erpnext/blob/4b5f8c5bea3bf73f10dc67c440ab5ef1f08a409a/erpnext/controllers/tests/test_mapper.py#L52-L70). Повторное применение источника к ещё не сохранённому документу должно сохранять число строк без дублей.
- Для нас: тест «двойное сохранение / два клика / повтор HTTP-запроса / перезапуск после ответа потерян» для карточек, товарных позиций, оплат, складских движений и прочих расходов. Помимо проверки интерфейса — `UNIQUE(request_key)` или уникальный бизнес-ключ на стороне базы, повторная выдача подтверждённого результата.

### 3. HomeBox: переносимый архив вместе с документами
- [service_exports.go, Manifest и версия схемы](https://github.com/sysadminsmedia/homebox/blob/4d19c9e4d23ae3e55c12c844e4810b494a0f1318/backend/internal/core/services/service_exports.go#L39-L57) и [Manifest с версиями и Counts](https://github.com/sysadminsmedia/homebox/blob/4d19c9e4d23ae3e55c12c844e4810b494a0f1318/backend/internal/core/services/service_exports.go#L199-L210).
- [copyAttachmentBlobs](https://github.com/sysadminsmedia/homebox/blob/4d19c9e4d23ae3e55c12c844e4810b494a0f1318/backend/internal/core/services/service_exports.go#L491-L551) упаковывает вложения по стабильному ID.
- Для нас: пакет `contracts-export.zip` со снимком SQLite, документами, подписью/печатью, настройками, версией схемы, временем и проверяемыми SHA-256 каждого файла; импорт только после проверок в отдельной staging-папке, резервная копия принимающего ПК и возможность отката; явный запрет молчаливой замены более новых данных.
- **Важная анти-практика:** в исходнике HomeBox при недоступности вложения экспорт логирует ошибку и пропускает файл; для юридически значимых документов нам это неприемлемо. Наш пакет должен завершаться как «неполный/ошибка», если обязательный файл отсутствует, или содержать проверяемый явный реестр отсутствующих файлов и блокировать автоматическое восстановление.

### 4. HomeBox / Grocy: небольшая автономная веб-система
- [HomeBox README](https://github.com/sysadminsmedia/homebox/blob/main/README.md): Go, SQLite и встроенный Web UI; демонстрирует концепцию локального сервера без Excel и обязательного интернета. Заявленные показатели памяти относятся к HomeBox, а не к нашему приложению.
- [Grocy README](https://github.com/grocy/grocy/blob/master/README.md): PHP + SQLite, API, браузер; можно изучить разделение веб-UI, API и хранения, но модель домашнего хозяйства не подходит для контрактов без значительных изменений.
- Для нас: сохраняем текущий HTML/CSS/JS и `localhost:8765`, меняем лишь backend на локальный Python + SQLite; Windows/macOS получают разные средства запуска, но общий формат пользовательских данных.

### 5. Litestream: резервирование SQLite через WAL
- [Архитектура Litestream](https://github.com/benbjohnson/litestream/blob/17e849b71639424c8ebe2fdbfc0e563f5bac2ae9/docs/ARCHITECTURE.md): снимки и репликация изменений WAL, восстановление из удалённого хранилища.
- Для нас: **кандидат на дополнительный слой** резервирования при наличии интернета; не заменяет базовое встроенное резервирование SQLite, копирование документов и проверки восстановления. Обязательность фонового процесса и требования к WAL требуют отдельного прототипирования. Пользователь предпочитает постоянную работу без интернета.

### 6. Restic: кроссплатформенные резервные архивы
- [Restic README](https://github.com/restic/restic/blob/master/README.md): поддерживает Windows/macOS/Linux, резервирование и восстановление, внешние хранилища. Кандидат на шифрованное сохранение **проверенной копии SQLite вместе с документами** на второй диск/в облако.
- Не копировать активный SQLite файл вручную в WAL-режиме: для снимка использовать SQLite Online Backup API ([официальная документация](https://www.sqlite.org/backup.html)), затем включить снимок в архив, сверить SHA-256, проверить восстановление отдельно.

### 7. Alembic и sqlite-utils: миграции базы
- [SQLAlchemy Alembic](https://github.com/sqlalchemy/alembic): версия схемы и управляемые миграции; актуально лишь если будет выбран SQLAlchemy. Не путать с одноимённым репозиторием alembic/alembic (3D scene format).
- [sqlite-utils](https://github.com/simonw/sqlite-utils): отдельный кандидат для экспорта/диагностики и операций со схемой. Прямого основания внедрять как обязательную зависимость сейчас нет.
- Для нас: `PRAGMA user_version` либо таблица версий; миграции на копии старой базы, последовательные проверки и отказ от неявного исправления повреждённых данных.

## Продукты для понимания бизнес-цикла (НЕ как основа для замены)
- [Dolibarr](https://github.com/Dolibarr/dolibarr) — договоры/заказы, поставщики, склад, платежи, отчёты; PHP + серверная СУБД, слишком большой для нашего локального приложения.

- [InvenTree](https://github.com/inventree/InvenTree) — Python/Django система глубокого складского учёта; **не использовать её код без проверки лицензии и адаптации СУБД**.
- [Frappe Books](https://github.com/frappe/frappe-books) — учёт закупок, продаж, платежей и склад; текущая браузерная версия требует инфраструктуру Frappe.
- [Part-DB](https://github.com/Part-DB/Part-DB-server) — товарные позиции электронных компонентов, SQLite, журналы изменений.
- [OpenContracts](https://github.com/Open-Source-Legal/OpenContracts) — обработка текста документов; не ERP и не система складского учёта.

## Практический приоритет будущих экспериментов
1. **Транзакции и идемпотентность (критично):** контракт ↔ резерв ↔ отгрузка ↔ факт оплаты без дублей. SQLite `BEGIN IMMEDIATE`, уникальные IDs операций, тест аварии на каждой стадии, независимая сверка сумм/остатков.
2. **Сохранность данных:** SQLite backup API, `PRAGMA integrity_check`, внешняя копия вместе с документами, тест восстановления, фиксация ошибок/хешей. Не затирать рабочий файл при сбое.
3. **Отказоустойчивый backend:** восстановление после сна Windows/перезапуска, безопасное закрытие, отдельный процесс backend и честные HTTP ошибки; локальный порт, закрытый от сети.
4. **Перенос Win↔macOS:** версионированный пакет данных и документов, проверка комплектности, отсутствие абсолютных путей, запрет конфликтующих экземпляров.
5. **Сохранение UX:** ныне действующий браузерный интерфейс, без навязывания ERP-экрана/Swift/Electron.
6. **Дополнительное резервирование:** оценить Restic и Litestream лишь после проверенного базового backup/restore.
