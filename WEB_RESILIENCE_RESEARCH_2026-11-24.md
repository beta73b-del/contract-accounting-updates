**Статус:** исследование GitHub-кода + проверка 7 сценариев на СИНТЕТИЧЕСКОЙ SQLite, без внедрения и без касания рабочей Excel-базы. Не является независимым аудитом или проверкой реальной установки.

**Область:** браузерная Web-версия «Контракты ИП» на Windows: интерфейс HTML/CSS/JS, локальный PowerShell / Excel COM / XLSX. **НЕ** отдельная Desktop/Tkinter/SQLite-программа в этом репозитории.

## A. Проверка документального хранилища — Paperless-ngx

[Paperless-ngx sanity_checker.py, строки 200–264](https://github.com/paperless-ngx/paperless-ngx/blob/faa6f09f289bad52fe8dce9d97ab9e121ae37e6b/src/documents/sanity_checker.py#L200-L264):
- на каждую запись о документе проверяется существование исходного файла, читаемость и совпадение сохранённого checksum;
- отдельно проверяется соответствие архивного файла и archive checksum;
- [sanity_checker.py, строки 283–319](https://github.com/paperless-ngx/paperless-ngx/blob/faa6f09f289bad52fe8dce9d97ab9e121ae37e6b/src/documents/sanity_checker.py#L283-L319) выявляет и предупреждает об «осиротевших» файлах, которые лежат в папке, но не привязаны к записям.
- [Paperless administration docs](https://github.com/paperless-ngx/paperless-ngx/blob/faa6f09f289bad52fe8dce9d97ab9e121ae37e6b/docs/administration.md#L302-L349): экспорт данных включает документы и manifest; для сопоставления существующих экспортированных копий можно запросить проверку checksum вместо сравнения лишь размера/времени.

**Кандидат для Web:** хранить в БД `file_id`, `contract_id`, относительный путь, размер, SHA-256, признак/тип документа, дату добавления; сохранять исходные документы без потери имени; периодический `document_check` подтверждает файл+хеш, отдельно выдаёт сиротские файлы и некорректные ссылки. Если вложение отсутствует, **не удалять карточку и не считать резервную копию комплектной**. Вложение необязательно при создании контракта, но если ссылка на него сохранена, файл обязан присутствовать в проверенном архиве.

**Существенный риск:** операция над файлами и SQL транзакция не становятся автоматически одной ACID-транзакцией. В [Paperless tasks.py, строки 422–494](https://github.com/paperless-ngx/paperless-ngx/blob/faa6f09f289bad52fe8dce9d97ab9e121ae37e6b/src/documents/tasks.py#L422-L494) обновление метаданных и перемещение файла выполняются в управляемом участке, но простое `shutil.move` не «откатывается SQL rollback». Поэтому для нашей задачи нужна собственная схема staging + транзакционная запись состояния перемещения + атомарное переименование на одном томе + восстановление незавершённых операций после перезапуска + hash check. Это **проектное предложение**, код не реализован.

## C. Надёжность SQLite — первичные источники

- [SQLite: Online Backup API](https://www.sqlite.org/backup.html) создаёт согласованный снимок работающей базы; в Python доступен `sqlite3.Connection.backup()`. Копирование одного открытого `.db` в WAL-режиме **не является допустимым универсальным резервированием**.
- [SQLite: WAL](https://www.sqlite.org/wal.html): незакрытый `-wal` является частью состояния БД, возможны `SQLITE_BUSY`, checkpoint starvation, нельзя использовать рабочую WAL-базу через сетевой/синхронизируемый каталог. Веб-приложение должно хранить базу на **локальном SSD**; облако — только назначение готовой проверенной копии.
- [SQLite: PRAGMA](https://www.sqlite.org/pragma.html): `PRAGMA integrity_check` **не проверяет** внешние ключи — нужен ещё `PRAGMA foreign_key_check`. Установка `PRAGMA foreign_keys=ON` требуется для каждого соединения. Проверять реальные значения применённых настроек, а не рассчитывать на отсутствие ошибок при опечатке.
- `journal_mode=WAL` + `synchronous=FULL` — кандидат для надёжной локальной сборки (более сильная защита подтверждённого COMMIT от отключения питания, чем NORMAL), но требует измерения на SSD Windows/Mac и тестов.
- **КРИТИЧНО для выбора версии:** [официальное описание SQLite WAL-reset bug](https://www.sqlite.org/wal.html#wal_reset_bug): редкий сценарий повреждения при нескольких соединениях; исправление в SQLite **3.51.3 (13.03.2026)** и в отдельных backport **3.44.6, 3.50.7**. Не следует слепо полагать, что установленный Python включает новую SQLite. В каждом выпускаемом бинарнике на Windows/macOS проверять `sqlite3.sqlite_version` и подтверждать patched build; не использовать старую библиотеку при многопоточном WAL без понимания риска. Обнаружение не говорит, что у текущей Excel-версии есть эта проблема.
- [Restic check code, строки 27–42](https://github.com/restic/restic/blob/master/cmd/restic/cmd_check.go#L27-L42): обычный `check` проверяет структуру архива, для сверки содержимого требуются `--read-data` или `--read-data-subset`. Проверка наличия архива недостаточна для доказательства восстановления.
- [Paperless-ngx](https://github.com/paperless-ngx/paperless-ngx/blob/faa6f09f289bad52fe8dce9d97ab9e121ae37e6b/docs/administration.md): данные и документы должны экспортироваться вместе; контроль воссоздания нужен после импорта.

## E. Предлагаемая модель согласованных документов и бизнес-операций (ЕЩЁ НЕ РЕАЛИЗОВАНА)

1. **Одна бизнес-транзакция:** изменение статуса, резерва, складского движения и версии контракта. `BEGIN IMMEDIATE`; перечитать факт и доступность под блокировкой; записать операцию с уникальным `request_id` / `shipment_key`; в конце COMMIT; повторный запрос возвращает сохранённый результат.
2. **Уникальность:** `UNIQUE(contract_id, shipment_kind)` для однократного списания и отдельные ключи для разных допустимых операций; нельзя использовать один ключ для разных типов и сумм. Фактическая модель должна учитывать редактирование/отмену отправки/возвраты, не вводить новые статусы без согласования.
3. **Документы:** staged загрузка → вычисление SHA-256 → атомарное переименование на одном локальном томе → связанная запись статуса операции в БД. Сбой между файловым действием и COMMIT требует детерминированного повторного завершения/отката через журнал `pending_file_actions`. Проверять при запуске. Архивирование оплаченных документов должно сохранять нынешнее правило (не перемещать обратно автоматически). Блокировать небезопасное перезаписывание существующих файлов.
4. **Согласованный архив:** на время снимка блокировать/согласовать операции записи документов и БД; использовать Online Backup API; сохранить файлы; сверить все ссылки и SHA-256; manifest; архив переместить на резервный носитель; один раз в установленный период восстанавливать **в отдельную папку** и проверять контракты, склад, финансы и все документы.
5. **Финансы:** сумму хранить целым числом копеек или Decimal с явными правилами округления; сохранять вводимую сумму позиции как первичное значение, исключить двойной учёт расходов. Точная схема и месяц признания — только по текущей Web-логике и согласованию; никакого переноса чужих ERP-правил.
6. **Самостоятельная диагностика:** отображать «База доступна / только чтение / требуется восстановление», время последнего проверенного архива, несогласованные вложения и несоответствия журнала склада. Не пытаться автоматически «исправить» подозрительную базу.
