# Web «Контракты ИП»: архитектура резервного копирования в два независимых хранилища
Дата: 24.11.2026. Статус: техническое исследование и проектная спецификация; **не внедрено**, продуктивные XLSX/SQLite/JSON/документы и Desktop/Tkinter не изменены.

## 1. Цели, определения и ограничения
**Цель:** восстановить одновременное согласованное состояние контрактов, документов, склада, финансов, справочников и настроек после повреждения БД, сбоя приложения, отказа локального диска/ПК, ошибочного удаления, шифровальщика либо потери доступа к одному месту резервирования.

Не обещать нулевых потерь: два хранилища не обеспечивают RPO=0 при разрыве после последнего подтверждённого снимка, и не защищают от неверных данных, которые уже попали в оба архива. Выбранный целевой RPO: <=30 минут при включённом ПК, доступном интернете и успешных снимках; при офлайн — локальный RPO<=30 мин, удалённый RPO растёт до следующей доставки. Целевой RTO: проверить на реальном объёме и ПК; предварительный ориентир <=1–2 часов только для отработанного сценария, не гарантия.

Правило **3-2-1**: рабочий набор + локальная архивная копия на *другом физическом устройстве* + удалённая архивная копия (вне компьютера). Желательно 3-2-1-1-0: одна из копий неизменяемая/офлайн, ноль **обнаруженных** ошибок по итогам проверок. Отсутствие обнаруженных ошибок не равно доказанной абсолютной сохранности.

Нельзя считать C: и D: независимыми только по буквам: проверить PhysicalDrive/DeviceID. Нельзя считать папку Yandex.Disk/OneDrive автоматической независимой резервной копией: синхронизация удаления/порчи, права и риск шифровальщика. Возможно применять Яндекс.Диск только как **дополнительный** получатель архивных версионных файлов с запретом sync-delete, но ключевой второй источник — удалённое объектное хранилище с retention/immutability или эквивалентным append-only контролем доступа.

## 2. Окончательная базовая схема (предлагается)
- **Рабочее состояние:** локальный диск с SQLite (после миграции Web), attachments, настройки, вспомогательные JSON; пока текущий Web работает с XLSX и Excel COM, применять отдельный безопасный snapshot-XLSX/документов, а не переименовать XLSX в SQLite.
- **Координатор снимка:** один процесс с межпроцессной блокировкой, защищающий от одновременной смены DB/ссылок на документы. Записи через Web API и file operations координируются коротким barrier или generation-based immutable storage; если файлы можно менять напрямую вне приложения, на время копирования они должны быть заблокированы/версионированы. Только SQLite Online Backup API не делает снимок вложений согласованным.
- **Локальная staging-папка:** на рабочем диске, пока снимок не завершён; целевая папка final появляется только после полной проверки и атомарного rename на том же файловом устройстве.
- **Источник 1:** отдельный внутренний SSD/USB SSD/NAS с локальной историей архивов; сетевой NAS должен быть физически отделён и не иметь постоянных учётных данных администратора на клиенте. USB, который всё время подключен с правами удаления, НЕ защищён от шифровальщика. Дополнительный офлайн-USB — ценно.
- **Источник 2:** удалённое S3/S3-compatible хранилище, Object Lock + Versioning + retention и отдельные учётные данные с правами PutObject/GetObject/ListBucket **без** DeleteObject, изменения retention и lifecycle. До эксплуатации проверить конкретного провайдера: реальная поддержка governance/compliance, версии, Object Lock, защита удаления аккаунта, стоимость хранения/трафика/запросов, восстановление в нужном регионе. Вариант rest-server append-only — если отдельный доверенный хост администрируется независимо, но он не автоматически эквивалентен S3 Object Lock.
- **Источники независимы:** разные диски/поставщики/учётные записи; разные ключи шифрования и контроль доступа, но единый идентификатор снимка и manifest. Пароль резервирования хранить отдельно от компьютера, в защищённом менеджере + аварийная офлайн-копия; потеря ключа делает зашифрованный архив бесполезным.

## 3. Процедура создания единого снимка
1. Получить глобальный `backup_lock` (и file-generation barrier) и `snapshot_id` UUIDv4; проверить свободное место/доступность пути; журналировать start.
2. На время согласованной границы зафиксировать состояние связанных файлов; дождаться завершения текущих записей документов. Два подхода:
  A: блокировать все операции изменения БД и документов на время snapshot файлов; длительность измерять, не держать UI бесконечно.
  B: документы immutable/content-addressed; во время backup сформировать список ID+hash+generation и pin их версии до конца копирования; БД снять в согласованной границе. Это более масштабируемый итоговый вариант.
3. Для SQLite выполнить `sqlite3.Connection.backup()` в **новый** `snapshot.db` (никогда не заменять активный .db; не `copyfile(active.db)` при WAL), закрыть и открыть снимок read-only; выполнить `PRAGMA integrity_check` (ожидать единственное `ok`), `PRAGMA foreign_key_check` (ожидать 0 строк), сверку счётчиков/неизменяемых бизнес-инвариантов (в т.ч. contract↔docs↔stock). Проверить необходимые вспомогательные БД/JSON.
4. Для текущей **Excel Web**-версии вместо пункта 3 использовать отдельное согласованное закрытие записи/Excel COM snapshot или другой способ безопасного копирования книги с проверкой исходной схемы, если Excel остаётся открытым: процесс документировать и тестировать на реальном Windows. Не считать простую копию открытого XLSX доказательством целостности.
5. Скопировать все referenced attachments + дополнительные пользовательские файлы/настройки из whitelist; относительные пути без `../`; вычислить SHA-256 каждого; missing/changed referenced attachment → ERROR, готовый полный снимок запрещён. Необязательные вложения (их нет) не ошибка.
6. Составить `manifest.json`: format_version, created_utc, snapshot_id, parent_data_revision, app/schema version, source_host_id (не ПДн), тип источника, список path,size,sha256, общее число контрактов/позиций/движений/расходов/вложений, статусы validation, checksum всего архивного пакета вне его. Manifest внутри архива защищён подписью/MAC либо шифрованием с аутентификацией при выбранном формате, иначе один только SHA256 не обеспечивает защиту от злоумышленника.
7. Упаковать набор в стандартный портативный архив и зашифровать AEAD (либо использовать штатный аутентифицированный архиватор, например restic; не реализовывать криптографию самостоятельно). Сначала validate содержимое/архив и внешний hash. Готовый локальный immutable filename: `contracts-YYYYMMDDTHHMMSSZ-<uuid>.backup` (никаких имён latest, перезаписываемых поверх).
8. Вызвать атомарный rename из staging в finalized на локальном томе; только после этого считать snapshot READY. Сохранить журнал о хеше, размере, длительности, статусах.
9. Разнести **тот же snapshot_id и тот же архив**: отдельно в локальный источник и удалённый. Если локальный диск недоступен, удалённая доставка всё равно предпринимается; сбой одной копии не блокирует вторую. Нельзя удалять staging/локальную очередь, пока хотя бы одна обязательная доставка не восстановилась по политике удержания.
10. Удалённая доставка: upload в уникальный ключ; проверить размер, object version id, retention, скачивание и SHA256 (полная проверка непосредственно после запуска/периодически; не полагаться только на ETag у multipart/SSE). Отдельные статусы source1 and source2; повтор запроса должен быть idempotent; при конфликте hash — явная ошибка, никогда не переписать старый объект.
11. Для локальной копии прочесть файл и проверить SHA256 после записи. Не выдавать «две копии сделаны», пока оба независимых источника не подтвердили свои копии.
12. Проверять успешный test-restore в staging-папку: расшифровать, распаковать, SHA256 всех файлов, SQLite pragmas + cross-check ссылок, числа записей, склад/финансы. Не переключать работающую БД автоматически.

## 4. Запуск и политика
- Каждые 30 мин при работающем ПК; после события значимого изменения (оплата/отгрузка/массовое изменение) можно включить debounce snapshot, но не делать на каждый клик слишком дорогой архив.
- По запуску приложения и пробуждению ПК: если последний READY > 30 минут — catch-up; отдельный планировщик OS для backup вне открытого браузера (Windows Task Scheduler StartWhenAvailable, macOS launchd); не запускать два backup одновременно.
- При отсутствии сети — очередь локальных READY к отправке с exponential backoff; при возвращении связи передавать в правильном порядке, не очищая локальную историю преждевременно.
- Предлагаемая retention (требует оценки объёма): оба направления 48 часов получасовых; 30 дневных; 12 ежемесячных; 3 годовых. Для облака высокие расходы, если каждый полный архив большой; после нагрузочного теста можно уменьшить частоту полных снимков или использовать Restic с дедупликацией, но не снижать требуемое RPO без согласования.
- Удаление облачных версий — **только по отдельной серверной retention/lifecycle policy** со строгим минимальным сроком; ежедневный клиент не имеет права удаления. S3 Compliance mode нельзя укоротить до expiry: проверить режим перед выбором.
- Ежедневно после обоих источников: verify manifest, latest snapshot IDs, age, checksum выборочных архивов. Еженедельно полное скачивание/проверка хотя бы одного свежего облачного, ежемесячно полноценный test-restore из каждого хранилища. Для важных данных рекомендован ежедневный автоматический тестовый restore последнего снимка, если объём позволяет.
- Клиентское UI: последний **созданный** READY, отдельно дата/возраст последней **подтверждённой** копии LOCAL и REMOTE, очередь, ошибки/неполные документы, последний проверенный restore. Статусы BOTH_OK / LOCAL_ONLY / REMOTE_ONLY / FAILED / RECOVERY_REQUIRED и отдельно WARNING AGE > заданный RPO.
- Уведомление об отказе: сразу локально, повторно при >1 час несинхронизации; критическое >24 часа без удалённой копии или >1 час без обоих. Не отправлять пароль/названия личных файлов по уведомлениям.

## 5. Почему Restic не единственная обязательная копия
- Плюсы restic: AES/аутентифицированное шифрование, дедупликация, разные backend, snapshots, `check --read-data`, восстановление. Очень уместен для больших историй документов.
- Минусы: индекс/pack/lock зависимость repo, обслуживание `forget/prune` требует прав удаления и отдельно доверенного контекста. Append-only repository защищает от стандартного клиента с отсутствующими delete permissions, но не от компрометации административного аккаунта; S3 Object Lock на произвольном Restic repository может помешать нормальным операциям блокировок/прунинга, и нельзя заявлять совместимость без интеграционного теста.
- Первый надёжный этап — самостоятельные **версионные immutable архивы** с manifest, передаваемые в два хранилища; после реального замера размера перейти на content-addressed пакетирование/дедупликацию или вторичный независимый Restic repository, сохраняя полный restore test.
- Для облака предпочтительны уникальные архивные объекты со сроком retention и write-only credentials, а не двусторонняя синхронизация Yandex.Disk/OneDrive.

## 6. Матрица разрушительных сценариев (обязательные тесты)
| Отказ | Ожидаемая защита | Приёмка |
|---|---|---|
| Удалён рабочий SQLite | локальный/remote snapshot | точное test-restore в новой папке |
| Испорчен WAL/SQLite | валидный предыдущий SQLite backup | integrity/FK/business cross-check |
| Исчезли вложения | manifest и архивные docs | все referenced SHA совпадают, missing flagged |
| Сбой при сохранении документа | staged/pending_file_actions + barrier | либо файл+БД согласованы, либо ERROR |
| ПК выключился посреди снимка | .tmp никогда не READY | старый READY доступен; catch-up |
| ПК выключился посреди upload | уникальный object key и retry | remote статус не OK до проверки |
| Интернет выключен 3 дня | локальные READY + очередь | все архивы сохранены; cloud возраст отображён |
| Облачный архив испорчен/пропал | локальная копия + hash audit | full restore из LOCAL |
| Локальный диск исчез | remote immutable | full restore на новом компьютере |
| Удалён аккаунт облака | локальная независимая копия + offline USB | восстановление LOCAL; не обещать 100% |
| Шифровальщик с правом пользователя | remote immutable/no-delete, offline USB | не может стереть ранее retained versions |
| Хакер с админ-доступом к облаку | restricted roles; object lock Compliance (с оговорками) | deny delete/version overwrite within retention |
| Плохие данные корректно забэкаплены | история версий, business invariants | точка восстановления до повреждения найдена |
| Кража ПК/диска | удалённая копия + отдельно сохранённые ключи | восстановление на чистой ОС |
| Потерян пароль | неустранимый риск | offline emergency copy key и проверка доступа |
| Одновременно два backup | mutex/file lock | ровно один snapshot, без конфликтов |
| D: — лишь раздел того же диска | аппаратная сверка PhysicalDrive | не считать независимым назначением |

## 7. Какие данные включать
- после миграции: все активные SQLite (включая вспомогательные), документы/attachments, пользовательские шаблоны и файлы подписи/печати (если относятся к приложению), сохранённые JSON, локальные настройки, схемные версии, ID привязки файлов; исключить кэш/логи с ПДн без отдельной потребности; проверить, какие пути реально используются.
- пока Web на Excel: XLSX, вспомогательные JSON, каталог «Документы», настройки и другие реальные источники. **Не ограничиваться только будущей SQLite**, ибо она пока не рабочий источник Web.
- ссылки на документы хранить относительными. Не хранить в архиве пароли API/cloud credentials как обычные настройки; нужен отдельный аварийный recovery guide без секретов в GitHub.

## 8. Практические параметры перед внедрением (проверить, не выдумывать)
- Физические устройства и точки хранения текущего Windows ПК (C:, D:, съёмный носитель, NAS, Yandex.Disk); для отдельного Desktop известны D:\\UchetZakupok и рабочий LOCALAPPDATA, но это не Web.
- Объём XLSX/JSON/документов, средний прирост, количество файлов, свободное место локального источника, доступный канал загрузки; от этих величин зависят retention/стоимость и интервал.
- Реальный провайдер S3: стоимость запросов/хранения/загрузки, Object Lock/Versioning, независимая учётная запись, регион, физическая и юридическая доступность; без верификации провайдера не утверждать, что immutable существует.
- Согласованность живой Web Excel/PowerShell/COM под нагрузкой, порядок изменения файлов, максимальная продолжительность barriers; отдельная тестовая среда и копии рабочих данных.
- Обязательные испытания restore: Windows и Mac; код проверен синтаксически/модульно, интеграционно, и пользовательским запуском — отмечать раздельно.

## 9. Решение по этапам
B0: карта источников, размеров, физических носителей и реальных функций работы с файлами (read-only).
B1: isolated proof of concept с искусственной SQLite + файлами, включая отключение/ошибку/порчу; метрики.
B2: единый snapshot manager и manifest + verify + local copy/restore; Windows offline.
B3: отдельный remote adapter + Object Lock/append-only + идентификаторы/retention и backoff; тест невозможности delete.
B4: расписание, UI-контроль, регулярный unattended restore test, диагностика и тревоги.
B5: проверка текущей Excel-Web на **безопасной копии**, позднее переход к SQLite только после согласованной миграции; валидация двух целевых хранилищ, сборок Windows/macOS.

## 11. Проверка статуса
**Проверено по документации:** механизмы Online Backup API, два отдельных pragma, S3 Object Lock/Versioning, restic append-only, Windows TaskScheduler catch-up. **Проектное предложение:** точная схема согласованного manifest/queue/retention and notification, не интегрирована и не протестирована на пользовательском ПК. **Не выполнено:** подключение облака, шифрование тестового архива, создание двух хранилищ, тест переноса рабочей XLSX и фактическое test-restore пользователя. Рабочее приложение не менялось.
