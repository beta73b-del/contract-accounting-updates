### Критическое уточнение SQLite WAL-reset — 25.11.2026

В реальной Windows x64 PyInstaller QA-сборке подтверждена SQLite **3.45.1**, без исправления WAL-reset. Чтобы тестовый запуск не работал в уязвимом WAL, `Store` теперь выбирает **`journal_mode=DELETE`**, если `sqlite_build_safety.patched_wal_reset()` возвращает false. При подтверждённо исправленной SQLite допустим `WAL`. В обоих случаях `PRAGMA synchronous=FULL`. Обязательный выпускной барьер `python sqlite_build_safety.py --require-safe` по-прежнему нужен: автоматическое переключение режима — **не лицензия на продуктивный релиз со старой SQLite**. В тестах проверяется фактически выбранный режим и работа онлайн-копирования SQLite после записи.


## Согласованная политика резервирования — 25.11.2026

- Автоматический полный ZIP SQLite+документы+30-дневная Корзина: проверять при запуске и затем ежечасно, создавать не чаще одного раза за 24 часа; при неизменности состава/хешей не дублировать, но обновлять копию раз в 7 суток.
- Автоматически удалять только **проверенные программой собственные** `auto-*.zip` из `backups/automatic/`, если возраст **больше или равен 14 суткам** и осталась как минимум одна проверенная точка восстановления. При провале нового экспорта старые архивы не удалять независимо от возраста.
- Ручные полные архивы, копии для переноса и `before-v*.sqlite` перед схемными миграциями не очищаются этим правилом. Ручной импорт/восстановление только в отдельный новый каталог.
- Предлагать физически независимое второе хранилище; другая буква диска не доказывает независимость. Отказ USB/NAS не блокирует рабочую базу, но интерфейс обязан показывать, что второе место не подтверждено.
- Никогда не считать архив полным, если отсутствует хотя бы один записанный документ или нарушены SHA/SQLite. При исчезнувшей БД и сохранившихся папках запрещено создавать новую пустую базу на том же месте.
- Для будущего рабочего выпуска требовать патченную SQLite с исправленным WAL-reset: `sqlite_build_safety.py --require-safe`, проверка именно bundled runtime, не только версии Python. Сохранять предупреждение в QA при уязвимой SQLite, без рабочих данных.

# Правила SQLite LAB: сохранность пользовательских файлов

1. Любое удаление **пользовательского файла из каталогов приложения** должно проходить через `FileVault.trash_file` либо `FileVault.trash_legacy_attachment`. Прямой `unlink()` для активных документов запрещён. Допустимо удалять временные файлы только если они не являются единственными копиями пользовательского документа.
2. Срок хранения в Корзине 30 × 24 часа UTC. Файлы физически удаляет исключительно `FileVault.purge_expired` после проверки срока и SHA-256. Стирание не распространяется на финансовый журнал и складские проводки.
3. Хранить byte-данные по непрозрачным ID, никогда по неочищенному имени пользователя. Символьные ссылки, абсолютные пути, `..` и пути вне app-owned data root не обрабатывать.
4. Архив переноса должен включать SQLite, обычную папку `attachments/` и все активные/удалённые managed-файлы, срок восстановления которых не истёк. Прерывать экспорт при недостающих документах, неверном SHA/количестве, неподдерживаемой схеме, а также при незавершённой очистке.
5. Восстановление в папку, где уже есть данные, запрещено. При первом запуске выбирается архив до создания новой базы. Файлы и записи в рабочей Excel/Web-версии не меняются.
6. Любые изменения миграции SQLite должны сначала создавать проверенный онлайн-снимок, сохранять совместимость со старыми v1–v4 и иметь отрицательные тесты.
7. В отчётах различать: исходники написаны; unit-тесты прошли; архив реально прошёл Windows→Mac / Mac→Windows CI; установлено и проверено на личном ПК пользователя. Не смешивать эти статусы.
8. Не размещать в GitHub реальные базы, ZIP с документами, имена заказчиков, подписи, сканы, ключи и персональные сведения. Синтетические ZIP-файлы CI — без реальных данных.
9. Настоящий прототип не является готовой заменой действующей Excel-версии; полная функциональная parity обязательна перед переключением.
