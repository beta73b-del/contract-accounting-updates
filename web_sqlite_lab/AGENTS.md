# Правила SQLite LAB: сохранность пользовательских файлов

1. Любое удаление **пользовательского файла из каталогов приложения** должно проходить через `FileVault.trash_file` либо `FileVault.trash_legacy_attachment`. Прямой `unlink()` для активных документов запрещён. Допустимо удалять временные файлы только если они не являются единственными копиями пользовательского документа.
2. Срок хранения в Корзине 30 × 24 часа UTC. Файлы физически удаляет исключительно `FileVault.purge_expired` после проверки срока и SHA-256. Стирание не распространяется на финансовый журнал и складские проводки.
3. Хранить byte-данные по непрозрачным ID, никогда по неочищенному имени пользователя. Символьные ссылки, абсолютные пути, `..` и пути вне app-owned data root не обрабатывать.
4. Архив переноса должен включать SQLite, обычную папку `attachments/` и все активные/удалённые managed-файлы, срок восстановления которых не истёк. Прерывать экспорт при недостающих документах, неверном SHA/количестве, неподдерживаемой схеме, а также при незавершённой очистке.
5. Восстановление в папку, где уже есть данные, запрещено. При первом запуске выбирается архив до создания новой базы. Файлы и записи в рабочей Excel/Web-версии не меняются.
6. Любые изменения миграции SQLite должны сначала создавать проверенный онлайн-снимок, сохранять совместимость со старыми v1–v4 и иметь отрицательные тесты.
7. В отчётах различать: исходники написаны; unit-тесты прошли; архив реально прошёл Windows→Mac / Mac→Windows CI; установлено и проверено на личном ПК пользователя. Не смешивать эти статусы.
8. Не размещать в GitHub реальные базы, ZIP с документами, имена заказчиков, подписи, сканы, ключи и персональные сведения. Синтетические ZIP-файлы CI — без реальных данных.
9. Настоящий прототип не является готовой заменой действующей Excel-версии; полная функциональная parity обязательна перед переключением.
